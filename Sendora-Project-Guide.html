Sendora – Complete Project Guide

Everything about this project in one page: what it does, what each file is for, how the backend and frontend talk to each other, and flow charts of every important process. Written so a complete beginner can follow it.

1. What is Sendora?

Sendora is a personal job-search assistant built as a web app. It helps one person (the "owner") do three boring but important things faster:

✉️ Cold email outreach
You paste a job description and a recruiter's name. AI writes a polite email, you review it, and Sendora sends it from your own email account with a resume attached.
📄 AI resume builder
You paste a job description. AI picks your most relevant projects and rewrites your resume (in LaTeX) for that job. Sendora compiles it to a PDF you can download or attach.
🧠 Knowledge base
The place where you store the facts the AI uses: your project descriptions and your master resume. Better facts in → better resumes out.
📥 Email categorizer
Reads an incoming email and labels it (interview invite, rejection, spam…), with a priority and a suggested reply. The backend is ready; the screen in the UI says "Coming Soon".
Two kinds of visitors. Because this is a portfolio project, anyone can open the site and try the AI features (Viewer / guest mode), but only the owner (who knows a secret passcode) can send real emails or change saved data. See section 9.

2. Concepts you need first

If these words are new to you, read this section. Everything else builds on it.

TermPlain-English meaning

LLM / GeminiThe AI model (Google Gemini) that writes emails and resume text.

3. The big picture

Three programs/services cooperate. The browser never talks to the AI, database or mail server directly — it only talks to your backend, which holds the secrets.

One sentence per layer

  1. React frontend shows the screens and sends requests.
  2. Express backend checks who you are, validates input, then calls the AI / database / mail server / LaTeX compiler.
  3. External services (Gemini, MongoDB, SMTP) do specialised jobs and send results back.

6. How the backend works

6.1 Startup – server.js

  1. Loads the .env settings.
  2. Creates the Express app and turns on CORS (only the websites in CORS_ORIGIN may call it) and the JSON body parser (max 2 MB).
  3. Calls connectDB() to connect to MongoDB. If there is no MONGO_URI or the DB is down, the app still starts and keeps some data in server memory instead.
  4. Mounts every router under /api: /auth, /emails, /categorize, /resumes, /knowledge, plus /api/health.
  5. Adds a final error handler so a crash returns clean JSON instead of an empty page.

6.2 Authentication – authMiddleware.js and authRoutes.js

There are no user accounts. There is one secret passcode (OWNER_PASSCODE).

  • POST /api/auth/verify-owner – you send the passcode. If it matches (compared in constant time so timing can't leak it), the server returns a signed token that contains an expiry time (12 hours). The passcode itself is never sent back.
  • The frontend stores the token and attaches it to protected requests as the header x-owner-key.
  • requireOwner is a guard placed on a route: it checks the token's signature and expiry. No valid token → 403.
  • GET /api/auth/status tells the frontend whether its saved token is still valid.

6.3 Database connection – config/db.js

Connects once, retries at most every 15 seconds if it fails, and tells Mongoose not to wait around when disconnected. Controllers check connectDB.isConnected(); when false they use an in-memory array so the demo keeps working (data lost on restart).

6.4 AI – services/aiService.js

  • Reads GEMINI_API_KEY and the model name from GEMINI_MODEL.
  • generateEmail – turns a job description + recruiter name into {subject, body}. It is told not to add a sign-off because the server adds the signature itself.
  • categorizeEmailContent – asks Gemini for JSON: category, priority (P0–P5), sentiment, summary, deadline, suggested reply. The answer is validated and forced into allowed values.
  • generateCustomReply – writes a reply with your extra instructions.
  • If there is no API key, or Gemini errors / is rate-limited, every function returns a sensible fallback template so the UI never breaks.

6.5 Resume engine – services/resumeService.js

  1. Gather inputs: master resume LaTeX, the .cls style file, and all project READMEs (from MongoDB, disk, or built-in defaults – in that order).
  2. Ask Gemini to pick the N best-matching projects (1–5), reorder skills and tune bullets, keeping the exact LaTeX layout. Output must be raw LaTeX.
  3. Check the answer: must contain \documentclass and \end{document}; otherwise the base resume is used.
  4. Compile safely: the LaTeX is first scanned and rejected if it contains file-reading commands like \input or \write. Then XeLaTeX runs in its own throw-away folder with a 60-second timeout, shell access off, file access restricted, max 2 compiles at once. The folder is deleted afterwards.
  5. Return LaTeX + PDF (as base64 text) + metadata (target role, company, key skills, chosen projects, a file name).

6.6 Email sending – services/emailService.js

  • Keeps one reusable SMTP connection (with timeouts so it fails fast instead of hanging).
  • Removes any "Best regards" the AI added at the end, then appends a clean signature (name, LinkedIn, GitHub, LeetCode, resume link). All user text is HTML-escaped and only http(s) links are allowed in the signature.
  • Sends both a plain-text and an HTML version, with the PDF attached when provided.

7. How the frontend works

7.1 Startup

index.html contains an empty <div id="root">. main.jsx starts React and renders App.jsx into it. The whole site is a single page: clicking tabs changes what is shown without reloading.

7.2 Talking to the backend – api.js

export const API = (import.meta.env.VITE_API_URL || "/api").replace(/\/+$/, "");
// production: VITE_API_URL = https://your-backend.onrender.com/api
// local dev : falls back to "/api", and Vite's proxy forwards it to localhost:7000

Every fetch(`${API}/...`) in the app starts from this one constant, so you change the server address in exactly one place.

7.3 App.jsx – the main component

  • State (React's memory): which tab is active, the form fields, generated email, resume list, outreach logs, whether you are the owner, status banners.
  • On page load it checks /api/health (retrying for ~30 s because free hosting "sleeps"), then loads logs and saved resumes (owner only) and verifies any saved owner token.
  • Tabs: Outreach, Resume Builder, Knowledge Base, Email Categorizer (Coming Soon).
  • Outreach tab: fill job requirement + recruiter details → Generate with AI → edit the draft → choose a resume (existing / build new / none) → Send. Below it, a table of past emails.
  • Owner modal: asks for the passcode, stores the returned token in localStorage, and unlocks owner-only buttons. Locked buttons show a friendly "Viewer Mode" explanation instead of failing.

7.4 ResumeBuilder.jsx

  • Paste a job description, choose how many projects (1–5), click generate.
  • Shows the LaTeX code (editable) and a live PDF preview made from the base64 PDF.
  • Edit the LaTeX and press recompile to get a new PDF. Copy the LaTeX, download the PDF, delete saved resumes, or push a resume into the Send-Mail tab with "Use".

7.5 KnowledgeBaseManager.jsx

  • List, add, edit, delete and "feature" your projects (title, tagline, tech stack, README content).
  • Import a project from a GitHub URL with one click.
  • View, edit, save and reset the master resume LaTeX.
Beginner tip: React "state" is simply variables React watches. When setSomething(newValue) is called, React redraws the parts of the page that use it — that's how a banner appears after you click Send.

12. Security measures

The site is public and runs AI + a compiler, so many protections exist. These are good habits to learn from:

  • Secrets stay on the server (API keys, SMTP password, passcode live in .env, which Git ignores).
  • Signed expiring tokens instead of sending the passcode around; passcode compared in constant time; token signing key derived with scrypt (or OWNER_TOKEN_SECRET).
  • Rate limits on AI endpoints and on passcode guessing.
  • LaTeX sandbox: forbidden commands blocked, per-job temp folder, 60 s timeout, restricted file access, no shell escape, container runs as a non-root user.
  • Input limits: 2 MB request body, 10,000-character job descriptions, 100 KB GitHub README.
  • Output safety: email HTML is escaped, only http/https links allowed in signature, search text is regex-escaped.
  • CORS allow-list so only your own website can call the API from a browser (rejects all cross-origin calls in production if not configured).
  • Private lists: email logs and the saved-resume list require the owner token.

15. Deployment

  1. Backend → Render using backend/Dockerfile. The image is Node 20 on Debian with TeX Live (XeTeX + extra fonts), installs only production dependencies, runs as the node user, and has a health check on /api/health. Add all backend environment variables in Render's dashboard.
  2. Frontend → Vercel. Set VITE_API_URL to your Render URL ending in /api. Add your Vercel URL to CORS_ORIGIN on Render.
  3. Free Render servers sleep when idle; the first request can take 30–60 s. The frontend retries the health check to cope with this.

16. Known limits and gotchas

  • The Email Categorizer screen is not built yet — only its API exists.
  • GET /resumes/:id and the PDF link are public if someone knows the (hard to guess) id, because the PDF opens as a plain browser link.
  • In-memory fallback data disappears on restart.
  • The owner token lives in localStorage; it expires after 12 hours.
  • Rate limiting is per server instance (not shared across several servers).
  • If the Gemini model name is wrong, AI features quietly use fallbacks — check the message returned with generated content.
